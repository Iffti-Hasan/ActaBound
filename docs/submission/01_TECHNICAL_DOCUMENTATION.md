## 1. Executive Summary & Problem Formulation

### 1.1 The Vulnerability of Unbounded Autonomous AI in Web3
The emergence of Large Language Models (LLMs) as autonomous economic participants introduces an unprecedented systemic challenge to decentralized finance. Traditional automated agents (e.g., arbitrage bots, limit order executors) rely on static, deterministic code. Conversely, generative AI models operate probabilistically, translating natural language goals into execution actions through statistical token prediction.

When developers grant an autonomous LLM direct signing authority or broad account abstraction paymaster rights, four catastrophic failure modes emerge:
1. **Adversarial Prompt Injection (OWASP LLM01):** Malicious third parties embed adversarial instructions inside transaction metadata, ENS names, or contract calldata, coercing the LLM into altering transfer destinations or siphoning funds.
2. **IEEE 754 Floating-Point Accounting Drift:** Standard JavaScript floating-point calculations (`0.1 + 0.2 = 0.30000000000000004`) introduce precision errors when converting fractional currency to atomic token units. Attackers can exploit rounding boundaries to execute micro-drain attacks or bypass boundary checks.
3. **Time-of-Check to Time-of-Use (TOCTOU) Calldata Tampering:** Calldata or recipient parameters may be intercepted and altered between the moment an LLM approves a plan and when the signed transaction is broadcast to the mempool.
4. **Direct Private Key Exposure:** Placing private keys in the LLM's operational context, system prompts, or memory cache exposes raw keys to extraction attacks via jailbreak prompting.

### 1.2 The ActaBound Solution: Bounded Authority
ActaBound resolves these failure modes by enforcing a fundamental separation of concerns: **Bounded Authority**. 
- The **AI Planning Agent** functions strictly as an unprivileged, probabilistic intent interpreter. It parses natural-language prompts and proposes structured execution plans, but **has zero custody or knowledge of private keys**.
- The **Policy Guard Engine** is a pure, deterministic mathematical state machine. It evaluates every proposed transaction against an immutable, human-signed **Mandate** using exact `BigInt` integer arithmetic.
- The **Financial Twin** performs pre-flight predictive balance sheet modeling, computing post-execution reserves, slippage tolerance, and safe spending margins.
- The **Isolated Signer Enclave** stores cryptographic keys encrypted with AES-256-GCM. It signs transactions *only* when presented with an immutable permit hash generated by the deterministic policy engine.
- Every event is linked into a sequential, tamper-evident **Evidence Ledger** using SHA-256 block hash chaining.

### 2.2 Security Boundaries & Information Flow
1. **Boundary A (User $\to$ Gateway):** User issues a high-level financial instruction via the AI Command Center or UI.
2. **Boundary B (Gateway $\to$ AI Planner):** The instruction passes through the input sanitizer to neutralize prompt override heuristics. The LLM translates the intent into a `StructuredPlan` validated by a strict `Zod` schema.
3. **Boundary C (AI Planner $\to$ Policy Engine):** The structured plan is delivered to the deterministic policy engine. The policy engine accesses the active user mandate from persistent storage.
4. **Boundary D (Policy Engine $\to$ Financial Twin):** The twin computes pre-flight balance deltas. If `amount > availableBalance - protectedReserve`, the twin signals an immediate constraint breach.
5. **Boundary E (Policy Engine $\to$ Evidence Ledger):** The decision (`ALLOW` or `BLOCK`) and the canonical SHA-256 fingerprint are recorded into an append-only block.
6. **Boundary F (Policy Engine $\to$ Signer Enclave):** If and only if the decision is `ALLOW`, the engine passes the canonical transaction fingerprint to the isolated signer.
7. **Boundary G (Signer Enclave $\to$ Blockchain):** The signer decrypts the private key inside the enclave, signs the secp256k1 transaction, and broadcasts it to the Sepolia RPC node.
8. **Boundary H (Blockchain $\to$ Evidence Ledger):** The on-chain transaction receipt (tx hash, block number, gas used) is verified and permanently sealed into the ledger.

## 3. Core Algorithm Description & Mathematical Invariants

### 3.1 Algorithm 1: Exact BigInt Currency Normalization
To prevent floating-point drift, all token values are parsed into standardized integer units:

$$\text{RawUnits} = \left\lfloor \text{Amount} \times 10^{\text{decimals}} \right\rfloor$$

```typescript
export function parseTokenUnits(amountStr: string, decimals: number = 6): bigint {
  const clean = amountStr.trim().replace(/,/g, '');
  const parts = clean.split('.');
  const wholePart = parts[0] || '0';
  const fracPart = (parts[1] || '').slice(0, decimals).padEnd(decimals, '0');
  const wholeUnits = BigInt(wholePart) * (10n ** BigInt(decimals));
  const fracUnits = BigInt(fracPart);
  return wholeUnits + fracUnits;
}
```

**Mathematical Invariant 1 (Zero Float Drift):**  
$$\forall a, b \in \mathbb{Q}, \quad \text{Parse}(a) + \text{Parse}(b) \equiv \text{Parse}(a + b) \pmod 1$$
No fractional token value is ever lost or gained due to binary floating-point representation.

### 3.2 Algorithm 2: Deterministic Policy Evaluation Engine
The policy engine evaluates five non-negotiable predicates in sequential, fail-closed order:

```
Algorithm PolicyEvaluate(Plan P, Mandate M, State S):
  Input: StructuredPlan P, ActiveMandate M, CurrentState S
  Output: PolicyDecision { decision: ALLOW | BLOCK, reasonCode, fingerprint }

  1. If CurrentTimestamp() >= M.expiryTimestamp Then
       Return BLOCK("MANDATE_EXPIRED")
  2. If M.status == REVOKED Or S.isEmergencyPaused Then
       Return BLOCK("MANDATE_REVOKED")
  3. If P.destination Not In M.allowedDestinations Then
       Return BLOCK("DESTINATION_NOT_ALLOWLISTED")
  4. If P.assetIn Not In M.allowedTokens Then
       Return BLOCK("TOKEN_NOT_ALLOWLISTED")
  5. If P.amountUnits > M.maxTransactionLimitUnits Then
       Return BLOCK("EXCEEDS_TRANSACTION_LIMIT")
  6. If CurrentTimestamp() >= S.lastResetTimestamp + 86400 Then
       S.currentDailySpentUnits = 0n
       S.lastResetTimestamp = CurrentTimestamp()
  7. If (S.currentDailySpentUnits + P.amountUnits) > M.dailySpendingLimitUnits Then
       Return BLOCK("DAILY_BUDGET_EXCEEDED")
  8. If (S.currentBalanceUnits - P.amountUnits) < M.protectedReserveUnits Then
       Return BLOCK("RESERVE_BREACH")
  9. If P.slippageBps > M.maxSlippageBps Then
       Return BLOCK("SLIPPAGE_EXCEEDED")

  10. S.currentDailySpentUnits = S.currentDailySpentUnits + P.amountUnits
  11. Fingerprint = SHA-256(P.assetIn || P.destination || P.amountUnits || S.nonce)
  12. Return ALLOW("PERMITTED_WITHIN_MANDATE", Fingerprint)
```

**Mathematical Invariant 2 (Reserve Floor Guarantee):**  
Let $B_t$ be the token balance at time $t$, $R$ be the protected reserve floor, and $\Delta x$ be the proposed transfer:
$$B_{t+1} = B_t - \Delta x \ge R \quad \Longleftrightarrow \quad \Delta x \le B_t - R$$
If $\Delta x > B_t - R$, the policy engine rejects the transaction with probability $P(\text{Reject}) = 1.0$.

### 3.3 Algorithm 3: Financial Twin Predictive Balance Sheet Modeling
Before execution, the Financial Twin computes the predictive state vector:

$$\mathbf{S}_{\text{projected}} = \begin{bmatrix} B_{\text{USDC}} - \Delta x \\ V_{\text{Total}} - \Delta x \\ D_{\text{Spent}} + \Delta x \\ D_{\text{Remaining}} - \Delta x \end{bmatrix}, \quad \mathcal{M}_{\text{reserve}} = (B_{\text{USDC}} - \Delta x) - R$$

Where $\mathcal{M}_{\text{reserve}}$ is the **Reserve Margin**. 
- If $\mathcal{M}_{\text{reserve}} \ge 0$, the state transition is feasible.
- If $\mathcal{M}_{\text{reserve}} < 0$, the system generates an alternative suggested transfer:

$$\Delta x_{\text{suggested}} = \min\left( M_{\text{single\_tx}}, \, B_{\text{USDC}} - R, \, D_{\text{Remaining}} \right)$$

### 3.4 Algorithm 4: Cryptographic Evidence Block Hash Chaining
Auditability is guaranteed by recursive SHA-256 block hashing:

$$H_0 = \text{SHA-256}(\text{"ACTABOUND_GENESIS_BLOCK"})$$

$$H_n = \text{SHA-256}\Big( H_{n-1} \,\|\, \text{SHA-256}(\text{Payload}_n) \,\|\, n \,\|\, T_n \Big)$$

Where:
- $H_n$ is the block digest of block $n$.
- $H_{n-1}$ is the previous block hash.
- $\text{Payload}_n$ contains: `{ prompt, structuredPlan, policyDecision, simulation, txHash }`.
- $n$ is the sequence number.
- $T_n$ is the ISO 8601 timestamp.

**Tamper Detection Theorem:**  
If any adversary alters record $k$ ($0 \le k < N$), then $\forall j > k$:
$$\tilde{H}_j \neq H_j$$
The verification function recomputes the chain from $H_0$ to $H_N$ in $O(N)$ time, detecting the exact block where corruption occurred.

## 4. Security Design & Threat Mitigation

### 4.1 Isolated Signer Enclave & Zero LLM Key Exposure
ActaBound enforces a strict cryptographic boundary separating the LLM reasoning process from key custody:

| Property | Implementation Detail |
| :--- | :--- |
| **Cipher Algorithm** | AES-256-GCM (Galois/Counter Mode) |
| **Key Derivation** | PBKDF2 with SHA-256 (100,000 iterations) |
| **IV Generation** | Fresh cryptographically secure random 12-byte IV per record |
| **Authentication Tag** | 16-byte GCM authentication tag verifying ciphertext integrity |
| **Memory Isolation** | Private key bytes are held in Node.js `Buffer` within the enclave and zeroed post-signature |
| **LLM Exposure** | **Zero.** The LLM memory context, prompts, and completions never contain key bytes |

### 4.2 On-Chain Smart Contract Vault (`BoundedExecutor.sol`)
As a secondary layer of defense, ActaBound deploys `BoundedExecutor.sol` on Ethereum Sepolia (Solidity 0.8.24):
- **On-Chain Budget Reset:** Automatically resets `currentDailySpent` every 24 hours (`block.timestamp >= lastDayResetTimestamp + 1 days`).
- **Inviolable On-Chain Reserve:** Evaluates `balance - amount >= protectedReserve`; reverts with custom error `ReserveBreach()`.
- **Replay Protection:** Tracks executed canonical fingerprints in `mapping(bytes32 => bool) executedFingerprints`.
- **Emergency Circuit Breaker:** Contract owner can call `pause()` or `revoke()` at any time to freeze all agent operations.
